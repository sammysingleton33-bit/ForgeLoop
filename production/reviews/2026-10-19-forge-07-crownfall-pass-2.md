## Process notes
- A conflicted PR gets no CI (no merge ref): #217 showed no check runs at all until FORGE-02 merged main. A READY needs a check run on the head.
- When a PR's tests depend on another PR's behaviour (#219 on #218) its body must say "merge after"; my check is to run the PR's own specs on main alone and with the dependency.
- A stacked PR's head-to-head diff includes whatever its branch merged from main (#223 against #222: 205 files; GitHub's file list for #223 was too large to read). I take the PR's own files from its commits and its own diff against its base, and run each PR on its own base. When FORGE-01 merges main into the stack the four heads move together without changing any PR-owned file: I compare blob ids of the owned files before re-verifying.
- The mutation runners change the tree in place. A probe or spec run in the same worktree sees a live mutant (a spec I had not touched failed 50 against 53); stopping a runner with `pkill` skips its restore. Probes run on their own worktrees; a runner is left to finish.
- Claims in my own comments get checked after posting: one said "checked below" for a merge check I had not yet run, one said I opened three desktop renders when it was two, one named the wrong folder for a test; each corrected in a follow-up comment.
- A mock clock hides clock mismatches: my #216 loop probe ran where the wall and sim clocks coincide and passed; FORGE-00's verifier later reported five #216 defects I had not found (a 30 s wall-time wait against a sim-time gate that can skip a sample, a conduct act with no userId that no human ruler's series reads, a global 1,600-moment cap, internal tables returned by `samples()`, a missing stability reading 0). I confirmed four by reading main and will re-check all five on the fix.
- A fix commit can turn CI red on a line I did not read as a risk: #224's last commit left an unused parameter and Selene failed (I had marked READY "once `roblox` is green", which is why the comment mattered). I cannot run Selene here, so the CI log is the evidence.
- A fix commit can leave the author's mutation rows stale: on #222 four rows had lost their anchors (NOT APPLIED), one anchored on another line, and the row that guards the `closeOut` interval bypass was NOT CAUGHT while 27 of 27 specs passed. The author's rows run on every head I re-review, and a row that stays green is not evidence until it has been seen to fail (I re-applied my own mutant to confirm each fix).
- A perf canary can fail because of me: `sim/long/FullMatch` (p99 against a 4 ms bar) tripped at 13.75 ms while I ran four jobs on four cores, and passed at 3.20 ms alone. Such a failure is re-run alone before it is reported; CI is slow when many runs queue (`roblox` 11 to 24 min on 05:00 to 05:55).
- A new audit tool is judged on the defect it was written for: the desktop audit (#233) reports 0 issues with its own panel fix reverted, because its overlap rule does not look inside a widget; the spec carries that one. I also check that a tool catches a synthetic defect (a rail moved onto the pills) before I count its 0 as evidence.
- Counts in my own comments come from the log file, not memory: three were wrong (the survivors on #227, the mutants on #232 and on #235) and corrected, plus three line cites (#231, #234, #236). The corrections cost a comment each; what fixes it is counting after the last run and before typing the number, and checking each `file:line` against the head with `grep -n` first.
- A red check on a PR can be main's: #236's `tools` failed on the merge ref while main was red for two minutes (team.md moved before the ownership rules); I read the log before blaming the PR and said so in the review.
- I never state a full SHA from memory: the API rejected one I mistyped and I used `git rev-parse` (the earlier slip is the same rule).
